# Factory versioning and release governance

Factory uses SemVer 2.0. The checked-in product baseline lives **only** in the repository-root `Directory.Build.props`. Development branches must not compete to change this file. The standalone `.NET 10` versioning CLI works offline without GitHub, tags, npm or a hosted version service.

## Version components

- `VersionPrefix`: product API/behavior release version, `MAJOR.MINOR.PATCH`.
- `FactoryReleaseChannel`: `preview`, `rc`, or `stable`.
- `FactoryReleaseSequence`: explicit fallback preview number for Git-free source archives, or the RC number. It is intentionally not updated on every PR.
- `VersionSuffix`: generated by MSBuild from the above settings, so direct `dotnet build` works without tooling (using the fallback preview sequence).
- The **official development build path** is `Build.ps1`. On a full Git checkout, it computes `preview.N` from `git rev-list --first-parent --count HEAD`. After an integration into `master`, the number increases automatically without modifying shared source files. The commit's 12-character SHA is added to `AssemblyInformationalVersion` as SemVer build metadata (`+g<sha>`).
- The generated `dist/build-manifest.json` records the effective SemVer, informational version, full source commit, timestamp and SHA-256 of the executable. It does not certify signatures or published releases.

Preview sequence numbers are **monotonic on `master`**, not gapless release counters. Different feature branches can have an equal preview count; the commit metadata distinguishes their binaries. The full Git history is required to calculate the revision; shallow repositories fail closed. An archive without a Git repository uses `FactoryReleaseSequence` and has no source SHA metadata.

## Local commands

From the repository root, with .NET 10 installed:

```powershell
# View the effective version for the current checkout.
dotnet run --project tools/Factory.Versioning -- build-version

# Run built-in isolated SemVer and XML round-trip tests.
dotnet run --project tools/Factory.Versioning -- self-test

# Make an explicit release-scope change on a dedicated branch, then open a PR.
dotnet run --project tools/Factory.Versioning -- bump patch
dotnet run --project tools/Factory.Versioning -- bump minor
dotnet run --project tools/Factory.Versioning -- bump major

# Stage a release candidate, advance to the next RC, or finalize stable.
dotnet run --project tools/Factory.Versioning -- channel rc
dotnet run --project tools/Factory.Versioning -- channel rc
dotnet run --project tools/Factory.Versioning -- channel stable

# Full build, tests, Windows publish and SHA-256 provenance.
.\Build.ps1
.\dist\Factory.exe version
```

Run only one `bump` option per intended product version change. `bump` resets the channel to preview. Calling `channel rc` a second time increments the release candidate number. Channel and product base changes must be reviewed in a PR targeted at `master`, with a documented compatibility decision.

**Note:** The CLI deliberately edits `Directory.Build.props` when `bump` or `channel` is used. Do not run mutation commands against `master`; prepare a short-lived release branch and obtain release-owner approval. The tools do not create commits, tags, GitHub releases, or merge PRs.

## SemVer interpretation

| Change | Release level |
| --- | --- |
| Compatible bug fix | PATCH |
| Compatible feature | MINOR |
| Breaking public contract after 1.0 | MAJOR |
| Experimental pre-1.0 compatibility change | Explicitly document impact; usually next MINOR |
| Any integration on master | New derived preview build revision, no product-level bump |

Version `1.0.0` is a separate readiness and approval decision. A version bump does **not** constitute release authorization. Preview builds are for development, RC builds require completed release-scope tests, and stable builds require verified build, tests, security/compatibility review, supported upgrade/backup plan, licensing review, and explicit publication approval. The existing `Factory release --project ...` command prepares **target repository** source archives; it does not publish Factory binaries or select Factory's own version.

## Parallel development and provenance

Agent work packages MUST NOT modify `Directory.Build.props` for ordinary implementation PRs. Versioning changes require a dedicated change owner and a PR. No agent edits `master` directly. The full first-parent commit count removes the shared-file race between parallel implementation agents. CI uses `fetch-depth: 0`, checks build/test outcomes, ensures executable and manifest versions agree, and verifies source SHA and binary hash. CI is validation only; it does not approve, merge, sign or distribute anything.

The SQLite `PRAGMA user_version` / persisted schema version, worker wire-protocol compatibility, and future provider adapter contracts are independent of the product SemVer. Do not conflate product updates with migrations or assume protocol backward compatibility. A released persisted schema requires an explicit supported upgrade/backup strategy; pre-release legacy databases remain subject to their documented limitations.
